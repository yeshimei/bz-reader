# 多语言支持评估

评估日期：2026-11-05　｜　基线：master @ 0.3.0（单包完整功能版）

## 实施进展

**P0 已落地（2026-11-05，commit `53b199d`）**：

- `src/i18n/`：`t` / `setLocale` / `detectLocale` / `onLocaleChange`；
  语言包是 TS 对象、编译进包体，不做运行时读盘。
- `src/plugin-commands.ts`：16 条命令的注册表抽成纯数据，id 是稳定契约、名字走 `t()`。
- ribbon + **91 处 `notify()`** 文案全部进语言包（含 data 层通知的调用侧）。
- 新增 `tests/i18n-coverage.test.ts`：再写 `notify('中文')` 会被这条闸拦下。

**语言来源：自动跟随 + 手动覆盖（commit `0eddc44`）**：

- 默认 `settings.language = 'auto'`，按 `getLanguage()` 跟随 Obsidian；
  设置页最前一组「界面」给三档：跟随 Obsidian / 中文 / English。
- 手动选择存 `data.json`（设备本地，不跟库走），切换后即时 `setLocale` + 重绘，
  并弹一条**新语言**的通知；**命令名只能下次启动生效**——`addCommand` 只在加载时求值。
- `auto` 但读不到宿主语言时退回中文（不是英文）；脏值一律落回 `auto`。

**默认语言仍是中文**，探测失败/语言无包一律退回中文。中文包是基准包，
英文包漏一条 key 由 `tsc --noEmit` 拦住（`Record<MsgKey, string>`）。

**`minAppVersion` 已提到 1.8.7，版本号随之升到 0.3.0（commit `c92baa7`）**：
官方 lint 的 `obsidianmd/no-unsupported-api` 把 `getLanguage()` 在 1.7.2 下判成
**error**（直接卡上架），所以提版本不是可选项。提版本必须连版本号一起动：`versions.json`
是「已发布版本 → 该版本 minAppVersion」的映射，只改 minAppVersion 会让同一个 0.2.0 出现
两种最低版本要求。0.2.0 及以前保持 1.7.2，老版本用户不受影响。

**八种语言全量改造（2026-11-05，commit `6644825`…`0d7cd12`）**：

按用户 2026-11-05 的决定，从两语言（zh/en）扩到八种：`zh`（基准）、`zh-TW`、
`en`、`ja`、`de`、`fr`、`es`、`pt`。

已完成迁移的模块（每一块都是**整块**做完，不留半翻）：

| 模块 | 文案量 | 说明 |
| --- | ---: | --- |
| 命令名 / ribbon / 91 条通知 | ~115 | P0 已完成 |
| 设置页 + 授权状态 | ~95 | 含字体档、强调色档、头栏图标、能力卖点四张集中表 |
| 书架页（书库） | ~30 | 页签、筛选、排序、空态、继续阅读卡 |
| 笔记页 | ~23 | 每日回顾、多选工具条、按书分组 |
| 统计页 | ~42 | KPI、年度目标、打卡、热力图、按书排行 |
| 阅读页侧栏 | ~29 | 目录/书签/划线/AI 四页签 |
| 划词工具条 | 8 | 想法/书摘/AI/双链/复制/删除 |

**三种组织方式，按「成套还是散装」分**：

1. **散装句子** → `src/i18n/<lang>.ts` 的扁平 key，八份包由
   `Record<MsgKey, string>` 强制齐。
2. **成套选项**（四色笔、三档字体、八档强调色、十颗头栏图标、十一条能力卖点）
   → 各自的 `Record<Locale, string>` 集中表（`COLOR_LABELS` / `FONT_LABELS` /
   `ACCENT_LABELS` / `LABELS` / `CAP_TEXT`）。理由：成套的东西拆进八份包后，
   漏翻一条**不会**让 tsc 报错（key 还在），只会让某个语言的用户在某一个档位上
   看到中文。集中表把「八种齐」变成类型约束。
3. **更新日志** → 唯一的双语例外：条目数据是 `{ zh, en }`，框架文案跟
   `changelogLang()` 走（zh/zh-TW 读中文，其余六种读英文）。

**结构上顺手修掉的一类坑**：模块级常量里存 label，切语言后不重算。
`FONT_FAMILIES` / `ACCENT_OPTIONS` / `HIGHLIGHT_COLORS` 去掉 `label` 字段，
`SIDE_TABS` / `STUDY_TABS` / `STUDY_ACTS` / `LIB_FILTERS` / `LIB_SORTS` /
`TOOLBAR_ITEMS` / `KEY_COMMANDS` / `headerActionSpec` 改存 `MsgKey`，
渲染时现取——否则切完语言重绘，看到的还是旧语言。

**新增的两道测试闸**（`tests/i18n-packs.test.ts`）：

- **占位符一致**：每个 key 在八种语言里的 `{name}` 集合必须与中文完全相同。
  类型看不出「德语把 `{n}` 写成了 `｛n｝`」，这条能。
- **字形健康**：拉丁语系包不许有汉字（抄漏了没翻）；日语包必须有假名
  （否则是英文原样抄过去）；繁中包与简中的条目至少六成写法不同
  （否则就是把 zh.ts 复制一份改文件名）。

**本轮没做的部分（下一轮）**：

- `src/shell/overlay.ts`：阅读页的弹层（排版面板、书库鸟瞰、书摘卡、
  删除确认、AI 翻译、年度海报、书籍详情、迁移确认）约 80 条。
  **刻意整块留白**——半翻的弹窗（一半英文一半中文）比整块中文更难看懂。
- `src/ui/import-panel.ts`、`src/shell/shelf-panel.ts` 的零散文案。
- `data` 层的错误消息错误码化（`license.ts` / `backup.ts` / `store.ts`）。
- 导出模板（`data/export.ts` 写进用户 vault 的 `tags: - 书摘`、`读到 N%`）。
- 内容排版（P4）与 RTL（P5）完全未动。

**P0 当时没做的部分**（P1–P2 范围，不是遗漏）：

- 壳层页面：书架 / 笔记 / 统计 / 设置页 / 侧栏 / 阅读器工具条 / 全部弹窗 / 更新日志。
  （设置页新增的「界面」组本身也还是中文标签：跟随 Obsidian / 中文 / English。）
- 颜色名（琥珀、朱红、松绿、黛蓝）与字体档名，仍只在中文里出现。
- `data` 层返回给人看的错误消息（`license.ts` / `backup.ts` / `store.ts` 的 `message`）——
  正确做法是错误码化，UI 层再翻；P0 只在调用侧包了外层句子。
- 内容排版（P4）与 RTL（P5）完全未动。

## 结论

> 以下三段是 **P0 之前的判断**，保留原样作为对照；P0 之后的实际状态见上面的「实施进展」。

**界面语言：零基础（P0 前）。** 没有 i18n 模块、没有语言包、没有语言切换，500 条用户可见文案
全部硬编码在渲染函数里。命令名、ribbon、通知、自绘设置页、更新日志、导出模板一律中文。
唯一已英文化的是 `manifest.json` 的 description 与 `README.en.md`——市场页能看懂，装进去
还是中文。

**内容排版：只适配了中日文一类。** 默认两端对齐且不开启断字（`hyphens` 全仓没有一处），
正文字距按汉字可读性给（`letter-spacing: 0.015em`），字体档只有宋体/黑体，TXT 一律标
`language: 'zh'`。EPUB 的 `dc:language` **被采集、被存进 schema，却没有任何代码消费它**——
信号已经有了，线没接上。

**两者是两件事，成本差一个数量级。** 界面语言是 49 个文件、约 500 条文案的系统改造；
内容排版是几个互相独立的开关。前者不做，海外用户装了也用不了；后者不做，中文用户读英文
原版书的体验也是残的。

### 当前架构对 i18n 的两面性

UI 全是纯函数拼模板字符串（`view*(vm) => string`），不是命令式 DOM 操作。这意味着：

- **好**：改造成本低——在渲染期插 `t()` 即可，不需要改组件结构；测试可以直接断言输出。
- **坏**：文案与 HTML 结构缠在一起（`'<div>还没有打开的书。</div>'`），抽 key 时得
  顺手把标签拆出去，否则 key 会绑死排版标记。

### 第 2 层 · 内容排版（读什么书都受影响）

| 缺口 | 证据 | 影响 |
| --- | --- | --- |
| 默认两端对齐、无断字 | `data/prefs.ts:86` `align: 'justify'`；`grep hyphens` 全仓 0 命中 | 英文书 + 窄栏会出现明显的词间大洞（rivers）。中文靠汉字等宽没这问题，所以一直没被发现 |
| 字距按汉字校准 | `engine/theme.ts:116` `letter-spacing: 0.015em` | 正文影响轻微；章题 `0.08em`（`theme.ts:145`）对西文偏松，标题会散 |
| 章题一律居中 | `engine/theme.ts:141-157` | 西文书的章题通常左对齐，这是中文书排版惯例 |
| 字体档只有中文 | `data/prefs.ts:105-109` | 「宋体 / 黑体」两档对英文用户无意义，且回退链里没有 Georgia / Charter 这类西文衬线 |
| TXT 语言硬编码 | `engine/txt.ts:158` `language: 'zh'` | 英文 TXT 被当中文，影响朗读选音、断字、屏幕阅读器 |

| RTL 完全不支持 | `engine/txt.ts:162` `dir: 'ltr'`；翻页方向固定 `prev/next` | 阿拉伯语/希伯来语书文字方向错、翻页方向反 |
| 竖排仅东亚有效 | `engine/theme.ts:86-88`（已是 pro 能力） | 对西文无意义，不算缺口，但说明「版式能力」本身是按语系分层的 |
| 书名题签 | `shell/adapt.ts:69-75` | **已适配**：中文取前两字，英文取首字母缩写 |
| 字数统计 | `engine/txt.ts:193-197` | **已适配**：汉字按字、西文按词 |

`meta.language` 的现状值得单独说：`data/book-meta.ts:171` 从 EPUB 读 `dc:language`，
写进 `EngineMeta`，存进 `bz-reader.json`——然后 `grep '\.language'` 只有这一处赋值，
全仓没有任何读取分支。这是本次评估最便宜的一个改造点：数据在手上，只差人接线。

### 第 3 层 · 写进用户 vault 的东西（比 UI 更敏感）

导出笔记里有中文固定串，会成为用户库里的永久内容：

- `data/export.ts:108` `读到 ${percent}%`、`${n} 条划线`、`${n} 个书签`

- `data/export.ts:151` `## 书签`
- `data/export.ts:117` 兜底章名 `未标注章节`

存储层用 ISO `YYYY-MM-DD` 是对的（不能本地化），但显示层没有走本地化格式。

| 缺口 | 证据 |

## 三、推荐方案

### 架构

1. **`src/core/i18n.ts`**：`t(key, params?)`、`setLocale(code)`、`locale()`、
   `onLocaleChange(fn)`。零依赖，纯函数，可单测。
2. **语言包放 TS 对象**，`src/i18n/zh.ts` / `src/i18n/en.ts`，esbuild 直接打进 bundle。
   不要运行时 `fetch` / `adapter.read` 语言包：插件要求离线可用，多一条读盘路径就多一类
   启动失败。
3. **key 用语义短名分域**（`shelf.empty`、`reader.page.next`、`tts.unsupported`），
   不用原文哈希、不用长句当 key。中文包是基准包，`zh.ts` 的 key 集合即类型的真源
   （`type Key = keyof typeof zh`），漏翻会在 `tsc --noEmit` 阶段红——这条能吃到现有
   三道门的红利，不需要额外 lint。
4. **语言来源**：`getLanguage()`（Obsidian 1.8.7+，返回 `zh` / `zh-TW` / `ja` / `ar`
   这类 ISO 代码），加上降级链 `localStorage['language']` → `moment.locale()` → `en`。
   `manifest.json` 的 `minAppVersion` 目前是 1.7.2，**提不提 1.8.7 是本次唯一需要拍板的
   兼容性决策**（见待决问题）。
5. **语言回退**：`zh-TW` 先找 `zh-TW` 再退 `zh`；未知语言一律退 `en`。不写「跟随内容
   语言」——界面语言是用户的，不是书的。
6. **体积**：`main.js` 现在 453 KB，500 条英文文案约 30 KB（+6.6%）。英文包不是负担，
   不必做按需加载。

### 测试策略（决定改造成本的关键）

现有 332 处中文断言是最大的隐性成本。推荐做法：**测试固定 `locale='zh'`**（与当前默认
一致），中文断言一条不改；新增少量英文断言单独写。代价是要在每个渲染测试的 setup 里
锁一次 locale，好处是 332 处断言全部保留，且中文文案回归仍在保护范围内。

反例（不推荐）：把断言改成「断言 key 存在」。那等于放弃「用户看到的字对不对」这层保护，
而文案恰恰是这个插件最容易被无意改坏的部分。

### 材料准备顺序

先做 **术语表（约 50 词）**，再动代码。理由：`划线 / 书摘 / 想法 / 标注 / 摘录` 这几个
词在中文界面里是分层的，直接机翻会全塌成 highlight / note / annotation。术语表定下来，
500 条文案的翻译才能一致；反过来先翻再统一，等于返工两遍。

术语表草案（高频词按出现次数排）：目录、阅读、书架、划线、章节、搜索、设置、想法、
标注、笔记、翻页、书库、导入、导出、统计、书签、卡片、授权、激活、竖排…

## 四、分阶段与成本

按「每次交付都能真机验收」切，不按文件切。

| 阶段 | 范围 | 文案量 | 估算 |
| --- | --- | ---: | --- |
| **P0 打地基** | `core/i18n.ts` + 语言探测 + 术语表 + 命令名/ribbon/`notify()` 98 处 | ~115 | 1–2 天 |
| **P1 壳层** | `shell/render/*`（书架/笔记/统计/设置）+ 侧栏 + 阅读器工具条 | ~200 | 3–5 天，含英文布局回归 |
| **P2 弹窗与日志** | `shell/overlay.ts`、`changelog*`、`about`、导入面板 | ~150 | 2–3 天 |
| **P3 数据面** | 导出模板、日期文案、AI 提示词、朗读语言 | ~10 + 逻辑 | 1–2 天 |
| **P4 内容排版** | `lang` 注入、断字、字体档、对齐默认值、TXT 语言探测 | 0（逻辑） | 2–3 天 |
| **P5 长尾** | RTL、更多语言包、更新日志多语言 | — | 按需 |

P0–P3 合计约 **8–12 人日**（含测试与布局回归），其中最大的不确定项不是翻译量，而是
**英文文案变长后的布局**：CSS 里有 43 处 `white-space: nowrap`、131 处固定 `px` 宽度、
47 处 `overflow: hidden`。中文 3 个字的地方换成英文常常是 3 倍字符宽度，最先破的是设置页
的分段按钮、书架筛选条、阅读页头部图标 tooltip。

P4 值得单独强调：**它不依赖 P0–P3**，对中文用户也立刻有价值（读英文原版书的人不少），
且改动面小、没有翻译成本。如果只想先拿一处收益，先做 P4。

---

## 五、不建议做的事

- **不做运行时语言包热加载。** 插件环境里多一条读盘/网络路径就多一类「启动即失败」，
  而收益只是「换语言不用重载」。
- **不追求官方语言表全覆盖。** Obsidian 支持 70 余种语言，其中完整翻译的只有几十种；
  插件追这个列表是纯负担。`en` 先跑通，`ja` 看数据再说。
- **不要一次抽完 500 个 key 再一起翻。** 先抽 P0 的约 115 条，在真机上把英文布局的问题
  暴露出来，再决定 P1 的排版要不要一起改。否则会在错误的布局假设上翻 400 条。
- **不要把「更新日志」的低成本做法搞复杂。** 它是每次发版手写的，双语维护成本高；
  P2 阶段建议只翻 `domain` 标签 + 保留条目中文（或直接英文一版、中文一版两份数据）。

## 六、商业判断（供决策，不替用户决定）

- 现状是「市场页英文、装进去中文」。海外用户从社区市场点进来、装上、看到满屏中文，
  留存基本为零——所以**只做 P0+P1 就足以让「能装不能用」变成「能用」**，后续阶段是打磨。
- 变现侧的现实约束：爱发电不支持海外支付。如果目标是海外收入，多语言只是前置条件，
  支付渠道是另一件事；如果目标是「让海外用户用上、给仓库涨星、给中文版引流」，
  P0–P1 的 ROI 是成立薄的了。
- 中文用户仍是付费主力。**任何多语言改造都不能让中文界面变差**——这是本仓的铁律级
  约束，也是推荐「测试锁 zh、新增 en」而不是「测试改 key」的原因。
